# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Project III — Edge AI bottle-cap counting on a mini conveyor. A YOLOv8n detector plus centroid tracking plus a virtual counting line, running on an Arduino UNO Q-class board (Qualcomm SoC, 2 GB RAM, Debian/Linux) and publishing JSON telemetry over MQTT to a PC dashboard.

Documentation and code comments are in Vietnamese; keep new comments and console output in Vietnamese to match.

## Two parallel deployments — pick the right one

The repo contains **two near-duplicate copies** of the same pipeline. There is no shared package: a change to one does **not** propagate, and the classes are deliberately named differently.

| | `product/` | `product_gd1/` |
|---|---|---|
| Target | the board (edge, headless) | PC, phase 1 ("Giai đoạn 1") development/training |
| Entrypoint | `src/main.py` | `src/main_pc.py` (has `--source`, `--model`, `--conf`, `--no-mqtt` CLI flags) |
| Config | `config/config.yaml`, `camera:` section | `config_pc.yaml`, `input:` section (`webcam_index`) |
| Classes | `CameraReader`, `ObjectDetector`, `MqttPublisher`, `Visualizer` | `VideoSource`, `ObjectDetectorPC`, `MqttPublisherPC`, `VisualizerPC` |
| Deps | `requirements.txt` (runtime only: opencv, numpy, paho-mqtt, pyyaml, psutil, onnxruntime) | `requirements_pc.txt` (adds ultralytics, torch, onnx) |
| Display | `show_window: false` | `show_window: true` |
| Model input | **224×224** (`IMG_SIZE` in `training/export.py`) | 320×320 |

`src/core/counter.py`, `tracker.py`, `color_analyzer.py` keep the same class names in both trees but the files have drifted. **When fixing a bug in counting, tracking, or color logic, check whether the same bug exists in the other tree and fix both.** The training/export scripts and dataset also exist in both copies; `product_gd1/training/dataset/` holds the real labelled images.

All commands below are run from inside `product/` or `product_gd1/` — both entrypoints `sys.path.append` their parent and resolve config/model/simulation paths relative to the CWD.

## Commands

```powershell
# PC development (product_gd1/)
pip install -r requirements_pc.txt
python src/main_pc.py                                        # GUI demo; q=quit, r=reset, SPACE=pause
python src/main_pc.py --source 0 --no-mqtt                   # webcam index, stream URL, or video path
python tests/test_simulation_accuracy.py                     # the only automated test (see below)

# Training pipeline (product_gd1/, needs ultralytics)
python training/collect_data.py --source 0                   # SPACE=capture, A=auto every 1.5s -> dataset/images/train/
python training/train.py                                     # 40 epochs, imgsz 320 -> models/yolov8n_cap.pt
python training/evaluate.py                                  # mAP50, precision, recall
python training/export.py                                    # .pt -> models/yolov8n_cap.onnx and .tflite

# Board (product/, over SSH)
python3 src/main.py
python3 tools/benchmark_board.py                             # per-stage timings, FPS projection, camera test
python3 tools/benchmark_board.py --skip-camera --sizes 224   # inference only

# Monitoring, on the PC (from repo root or product/)
python product/dashboard/monitor_subscriber.py               # subscribes lab/conveyor/counter, appends counter_records.csv
```

`training/evaluate.py` and `training/export.py` exist in both trees, but only `product_gd1/` can evaluate: `product/training/dataset/` holds a placeholder `data.yaml` and no images, so run `evaluate.py` from `product_gd1/`, passing the imgsz the board actually uses. `export.py` writes the ONNX next to the `.pt` it reads, i.e. straight over `models/yolov8n_cap.onnx` in whichever tree it runs — so exporting from one tree never updates the other, and an interrupted export leaves that tree's model clobbered (it is tracked in git, so `git checkout -- <path>` restores it). The LiteRT/TFLite half of `export.py` fails on Windows by design (`LiteRT export only supported on Linux x86 and macOS`); the ONNX half still succeeds.

There is no pytest, no linter, no CI. `tests/test_simulation_accuracy.py` is a standalone script: it generates a synthetic conveyor video with a known cap count (ground truth 12), runs the full pipeline headless, and prints `[TEST PASSED]` when counting accuracy ≥ 90%. Note it constructs `ObjectDetector(model_path="")`, so it deliberately exercises **mock heuristic mode**, not the trained model.

## Pipeline

`main` wires six stages per frame, in `src/main*.py`:

1. **`CameraReader`/`VideoSource`** — one of three sources selected by config `type`: `webcam` (V4L2), `stream` (RTSP/HTTP, e.g. an IP Webcam phone app), or `video` (mp4; auto-generated by `simulation/generate_synthetic_video.py` if missing). Buffer size 1 to minimise latency. `camera.index` takes an int or a device path; **on the board it must be a path like `/dev/video2`, because `/dev/video0` and `/dev/video1` are the SoC's Venus hardware video encoder/decoder, not the camera** — pointing at them opens successfully and then yields no frames. A UVC webcam claims the next two nodes (capture + metadata); find it with `v4l2-ctl --list-devices`. `camera.threaded_capture` runs a grab-only background thread that drains the V4L2 queue and decodes only frames that will actually be consumed; it defaults to **false** because it measured exactly neutral on this board (15.0 vs 15.0 FPS end-to-end). Turn it on only for a camera or driver that ignores `buffer_size` and accumulates latency, typically a network RTSP stream. Note that an earlier version which decoded *every* frame in the thread cost 3 FPS on this 4-core board — if you touch that loop, keep `grab()`/`retrieve()` split and keep both calls on the capture thread.
2. **`ObjectDetector`** — runtime chosen from the model file extension (`.pt` → ultralytics, `.onnx` → onnxruntime with `intra_op_num_threads=4`, `.tflite` → tflite-runtime). Three important fallbacks: it searches sibling extensions if the configured path is missing, and **falls back to `_heuristic_mock_detect` (contour circularity + aspect ratio) if the model is missing or fails to load** — so the system never crashes on a missing model, it silently degrades. Run with `detect_interval: N` to detect every Nth frame and reuse the previous boxes. `main.py` gates this on `(frame_count - 1) % detect_interval == 0`, so frame 1 always detects; do **not** reintroduce an `or not raw_detections` escape clause — an empty belt makes that condition permanently true, which silently disabled the interval exactly when the board was idle (measured effective interval 1.74 instead of 2, and 3.44 instead of 6). Stage 3's colour classification lives inside the same branch, so colours are computed once per detection rather than recomputed every frame over unchanged boxes.
3. **`ColorAnalyzer`** — HSV masks over the centre 50% ROI of each box, then a 4-tier decision in `classify_color`: single dominant colour (≥ 0.70 coverage), `multicolor` (3 colours within 0.12 of each other), dual-colour `"{c1}_{c2}"` (e.g. `red_white` for a Coke cap), or `unknown`. Colours outside `color.trained_colors` are reported as `unknown` by design — that is a requirement, not a bug.

   `color_ranges` holds 12 basic colours: red, orange, yellow, green, cyan, blue, purple, pink, brown, white, gray, black. The bands are deliberately **disjoint** (chromatic colours need `S ≥ 45, V ≥ 55`; achromatic are `S ≤ 44` split by `V`; `brown` is the low-`V` half of orange's hue band; `pink` is magenta plus a low-saturation red band) because `classify_color` sums coverage per colour independently — overlapping bands would double-count pixels and break the dominance, dual-colour and multicolor tiers. Roughly 4.8% of HSV space is intentionally unmatched (dark muted and pastel shades), which is what still yields `unknown`. Narrow the palette per deployment through `color.trained_colors` in the config, not by editing `color_ranges`.
4. **`CentroidTracker`** — Euclidean nearest-centroid matching with `max_distance=60`, per-ID trajectory history capped at 15 points, deregistration after `max_disappeared_frames`.
5. **`LineCounter`** — a cap counts when its trajectory's last two centroids straddle `line_y` in the configured `direction`. De-duplication uses `counted_ids`, which is intersected with the live tracker IDs each frame so the set cannot grow unbounded. Keeps `counts_by_color`.
6. **`MqttPublisher`** — non-blocking `connect_async` + `loop_start`; publishes on every count event and otherwise every `heartbeat_interval`. Payload: `{device_id, timestamp, total_caps, counts_by_color, fps, status}` on topic `lab/conveyor/counter`. Wraps paho-mqtt 1.x/2.x API differences.

Colours are matched from detection boxes to tracker IDs by nearest centroid within 40 px — this mapping is duplicated verbatim in `main.py`, `main_pc.py`, and the accuracy test.

Headless behaviour: `main.py` auto-disables the window on Linux when neither `DISPLAY` nor `WAYLAND_DISPLAY` is set (SSH), and instead prints a `[STATUS]` line every 15 frames.

## Tuning knobs that actually matter

- `counter.line_y` / `buffer_zone` — the usual cause of "caps pass but aren't counted"; must match the camera angle.
- `model.input_size` and `model.detect_interval` — the FPS levers on the board. **`input_size` must equal the `IMG_SIZE` the ONNX was exported with** (`training/export.py`), because the export uses `dynamic=False`. A mismatch does *not* fail at load: `_load_model` succeeds and the first `detect()` raises `INVALID_ARGUMENT`, which `main.py`'s broad `except Exception` swallows, so the process prints its banner, connects MQTT, then exits silently with status 0 and no `[STATUS]` lines. If the board goes quiet right after starting, check this first. Editing the config alone does nothing — re-export.
- Board tree ships 224×224. **Measured on the board itself** (`tools/benchmark_board.py`, 4-core aarch64): `ObjectDetector.detect()` takes 208.2 ms at 320×320 and 110.8 ms at 224×224, i.e. **1.88× faster**; everything else in the pipeline costs 3.56 ms together (colour 3.31, tracking 0.20, counting 0.06), so inference is ~97% of the frame budget. Accuracy cost on the 28-image val set: mAP50 0.9919 vs 0.9935, recall 0.9923 vs 0.9994 (mAP50-95 drops more, 0.810 vs 0.847, but that is box-localisation precision and counting only needs the centroid to cross the line).
- End-to-end on the board with the real camera: **~7 FPS before, 15.0 FPS now** at `detect_interval: 2`, and 19 FPS at `detect_interval: 3` — but only because `camera.fps` is 30; at 15 the camera itself caps the loop. The camera delivers ~23 FPS in MJPG, so at `detect_interval: 2` the pipeline (~15 FPS) and the camera are roughly balanced and raising `fps` further buys nothing.
- **This board has no usable NPU path.** Its `onnxruntime` 1.25.1 offers only `AzureExecutionProvider` and `CPUExecutionProvider`; there is no `QNNExecutionProvider`, and `onnxruntime-qnn` ships only for Windows-on-ARM, with no Linux aarch64 wheel. Driving the Qualcomm NPU/HTP would mean converting the model to `.dlc` with the QNN SDK or SNPE — a separate project, not a package install. Plan CPU-only.
- `detect_interval` is bounded by cap speed, not by taste: a cap must not travel more than ~30 px (half a cap diameter) between two detections, or `CentroidTracker` loses the identity and the count silently drops. Measured on the synthetic video: ≤32 px counts 12/12, 38 px counts 11, 45 px counts 7, 64 px counts 0.
- Do **not** reach for INT8 quantisation: `quantize_dynamic` measured 12× *slower* than FP32 on CPU, and `quantize_static` (QDQ, per-channel, 40-image calibration) detected 0 boxes at 320 and dropped recall to 0.59 at 224. YOLOv8's box-regression head does not survive naive post-training quantisation. If it must be tried, use `ultralytics export format=tflite int8=True` and re-validate before trusting it.
- `mqtt.broker` — `localhost` runs Mosquitto on the board itself; set it to the laptop's LAN IP to publish to the dashboard (Mosquitto 2.0+ needs `listener 1883` / `allow_anonymous true` to accept remote connections).
